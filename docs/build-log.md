- First 14 service tests (holds, bookings) all passed on the first run. I didn't trust an all-green first run, so I did quick manual mutation checks: (1) disabled the "seat already booked" check -> 1 test failed as expected; (2) removed the lazy `deleteExpiredForSeat` call in holdSeats -> ALL TESTS STILL PASSED. Gap: my TTL test called purgeExpired() (the sweeper) before re-holding, so the lazy-expiry path (expired hold row still present, sweeper hasn't run yet) was never exercised. Without that line a seat would stay locked up to 5s past expiry and the insert would hit the PK and report "just taken". Added a dedicated test; re-ran the mutation -> it now fails; restored -> 15/15 pass.
- Concurrency tests: (a) 30 parallel HTTP holds on one seat, (b) overlapping multi-seat pairs, (c) 8 worker_threads each with its OWN SQLite connection to the same file, released simultaneously via SharedArrayBuffer/Atomics (closest I can get to "two API instances" on one box). Honest caveat noted for README: (a)/(b) run in one Node process where better-sqlite3 is synchronous, so requests serialize anyway; (c) is the one that truly races.
  Validation by mutation: removing the seat_holds PRIMARY KEY -> 7 tests fail incl. all 3 concurrency tests. Switching the transaction from IMMEDIATE to DEFERRED -> the multi-connection test fails 3/3 runs (losers get a raw SQLite busy/snapshot error instead of a clean 409 SEAT_UNAVAILABLE), which is exactly why the code uses `.immediate()`. Restored -> 18/18.
